# Исторический арбитражный сканнер

Надстройка над калькулятором: вместо одной текущей котировки собирает
постоянно обновляемую историю заданной глубины, ищет по ней связки
`USDT → … → USDT` и строит график произведения курсов во времени.

Исходные модули (`arb_core.py`, `exchanges.py`, `dexes.py`, `app.py`)
не тронуты — они по-прежнему считают сделку по реальному стакану.

---

## Быстрый старт

```bash
pip install -r requirements.txt

python selftest.py              # 1. проверить, что источники доступны
python -m history.collector     # 2. запустить сбор (отдельное окно, не закрывать)
streamlit run app.py            # 3. интерфейс, страницы слева
```

Сборщик и интерфейс — разные процессы. Сборщик пишет в SQLite, интерфейс
читает. Браузер можно закрыть, сбор не остановится.

## Настройка

Всё в `history/config.py`, класс `Settings`:

| Параметр | По умолчанию | Смысл |
|---|---|---|
| `chain` | `bsc` | сеть DEX |
| `quote_asset` | `USDT` | вход и выход всех связок |
| `dex_pool_limit` | 200 | сколько пулов наблюдать |
| `dex_venue_quota` | 20 | гарантированная доля пулов на каждую площадку |
| `dex_venues` | список | площадки, у которых берём топ пулов отдельно |
| `watch_tokens` | пусто | тикеры, чьи пулы добираются принудительно |
| `dex_pull_seconds` | 300 | как часто снимать живые цены пулов |
| `min_pool_reserve_usd` | 100 000 | пулы меньше не берём: маржу съест проскальзывание |
| `history_days` | 7 | глубина истории |
| `timeframe` | `1m` | гранулярность |
| `max_legs` | 4 | максимум ног в связке |
| `trade_size_usd` | 1000 | объём, под который считается проскальзывание |
| `staleness_sec` | 180 | предельный возраст котировки |
| `spot_only` | `True` | отсекать токены с плечом (BTC3L, ETHUP и подобные) |

Те же значения переопределяются ключами командной строки:

```bash
python -m history.collector --days 30 --timeframe 5m --pools 200
python -m history.collector --no-dex        # только биржи
python -m history.collector --once -v       # один проход, подробно
```

## Как считается маржа

Маржа связки — произведение курсов всех ног, каждый уже за вычетом издержек:

```
итог / старт = ∏ ( курс_i × (1 − комиссия_i) × проскальзывание_i ) − газ
```

**Комиссии.** Для CEX — тейкерские ставки из `CEX_TAKER_PCT`. Для DEX
комиссия пула уже сидит в цене, отдельно не начисляется.

**Проскальзывание.** Для DEX точно, по формуле пула постоянного произведения:
своп размера `S` против резерва `R` даёт курс хуже спота в `R/(R+S)` раз,
где `R` — половина TVL пула. Для V3 ликвидность около текущей цены
концентрированнее, чем следует из общего TVL, поэтому оценка занижает
исполнимый объём — ошибка в безопасную сторону.

Для CEX точного расчёта нет: стакана в истории не существует, есть только
свеча. Используется оценка по обороту — сделка в долю `v` от минутного
оборота двигает цену примерно на `v/2`, с потолком 2%. Это ОЦЕНКА;
на ликвидных парах поправка близка к нулю и не искажает результат,
на неликвидных отсекает заведомо неисполнимое.

**Токены с плечом.** По умолчанию отсекаются: `spot_only = True`. Биржи
размещают BTC3L, ETHUP, BTCBULL и подобные на спотовом рынке, и ccxt честно
помечает их как spot — по флагам отличить нельзя. Для арбитража они непригодны:
внутри ежедневная перебалансировка позиции, цена следует за NAV, а не за
базовым активом, и видимая разница между площадками неисполнима. Распознавание
по имени: маркер плеча засчитывается, только если остаток имени сам торгуется
как обычный актив — иначе под шаблон попал бы токен, чьё имя случайно
оканчивается на UP или BEAR. Фильтр применяется и при сборе, и при расчёте,
поэтому уже накопленную историю пересобирать не нужно. Переключатель есть
в боковой панели на страницах связок и монитора.

**Свежесть.** Котировка старше `staleness_sec` в расчёт не идёт. Это
главный предохранитель: наивная протяжка застывшей цены фабрикует
арбитраж, которого не было. Внутри допустимого возраста протяжка
разрешена — иначе площадки почти никогда не совпадут по времени.

## Как ищутся связки

Прямой перебор невозможен: 80 активов и 4 ноги дают 512 тысяч маршрутов
в каждой из 10 тысяч точек истории — 5 миллиардов вычислений.

Поэтому два шага.

**Кандидаты.** Маржа — произведение курсов, в логарифмах — сумма.
Значит лучшую цепочку ищет алгебра max-plus: «умножение матриц», где
вместо суммы произведений берётся максимум сумм. Одно такое умножение
сразу даёт лучший двухшаговый переход между всеми парами активов;
повторное наращивание даёт три шага, четыре и так далее. Делается это
на прореженной по времени выборке (~400 точек).

**Точный расчёт.** Отобранные маршруты (обычно несколько сотен) считаются
уже по всей истории. Это дёшево и даёт полный временной ряд для графика.

### Почему поиск идёт от якоря

Полный перебор пар считает лучший переход между *всеми* парами активов —
это T·n³ операций. При шестидесяти активах доли секунды, при двухстах уже
миллиарды операций и минуты ожидания. Именно скорость, а не память,
держала потолок охвата на сорока активах.

Но цикл всегда начинается и кончается на якоре, и знать лучший путь между
произвольной парой не требуется. Достаточно релаксации от якоря: вектор
«лучший путь из USDT в каждый актив за k шагов» умножается на матрицу
курсов, T·n² операций на шаг. Замыкание цикла — прибавить курс обратно
в якорь.

Замеры на синтетической сетке: 150 активов × 288 точек — 1.7 с,
300 активов — 2.2 с, 400 активов × 144 точки — 1.5 с. Полный перебор
на тех же данных занял бы минуты.

Полная схема осталась и работает дополнительно, пока активов не больше
`DENSE_LIMIT` (60): она даёт больше разнообразия кандидатов, потому что
берёт верхушку по всем парам сразу, а не единственного лучшего
предшественника. Результаты двух схем объединяются.

### Сколько активов помещается

Потолок не задан числом, а считается от памяти: сетка занимает
T·n²·6 байт (float32 на курс плюс int16 на индекс площадки). Бюджет —
250 МБ в облаке, 1200 МБ локально, переопределяется переменной
`ARB_GRID_BUDGET_MB`. В интерфейсе ползунок «Активов в анализе» сам
раскрывается под выбранное окно и шаг, а подпись показывает, сколько
займёт сетка.

| Шаг и окно | Точек | Потолок в облаке |
|---|---|---|
| 5 мин × 6 ч | 72 | ~760 активов |
| 5 мин × 12 ч | 144 | ~537 |
| 5 мин × 24 ч | 288 | ~380 |
| 1 мин × 24 ч | 1440 | ~170 |

Восстановление маршрута берёт таблицы `argmax` того момента времени,
на котором маршрут был найден, — иначе для кандидатов из середины
истории восстанавливался бы не тот путь, что дал высокий балл.

### Сортировка

| Режим | Когда полезен |
|---|---|
| по доле прибыльного времени | по умолчанию: связка с редкими, но реальными окнами полезнее той, что стабильно чуть ниже нуля |
| по лучшей марже за период | искать пиковые возможности |
| по типичной марже | строгий критерий, чаще всего пусто — рынок эффективен |
| по марже в последней точке | что происходит прямо сейчас |

## Ограничения источников

| Источник | Что даёт | Лимит |
|---|---|---|
| ccxt (биржи) | OHLCV, до 1000 свечей за запрос | внутренний rateLimit каждой биржи |
| GeckoTerminal top-pools | цена и резерв 20 пулов за запрос | 30 запросов/мин, ключ не нужен |
| GeckoTerminal OHLCV | до 1000 свечей на пул | тот же лимит, 10 страниц пулов бесплатно |

Отсюда двухуровневая схема сбора DEX: текущие цены всех наблюдаемых
пулов обновляются за десяток запросов (~10 секунд), а история набирается
фоном по одному пулу за раз.

На бесплатной инфраструктуре исторические свечи DEX почти всегда
недоступны: лимит GeckoTerminal считается по адресу, а раннеры GitHub
делят адреса между тысячами проектов. Поэтому основной источник глубины
по DEX — не бэкфилл, а частые живые срезы: каждый прогон сбора длится
13 минут и снимает цены всех пулов раз в пять минут. Прошлое так
не восстановить, но плотность по времени вперёд получается та же.

### Откуда берутся пулы

Три источника, и второй с третьим появились не сразу:

1. **Топ сети по обороту.** Основа, но сортировка не смотрит на площадку.
   В BNB Chain оборот почти весь у PancakeSwap, и в сотне лучших пулов
   посторонних площадок практически нет. Пока источник был единственным,
   все найденные связки исполнялись в одном месте — хотя разница цен
   между площадками и есть предмет поиска.
2. **Топ каждой площадки отдельно** (`dex_venues`) — по одному запросу
   на площадку. Так в наблюдение попадают Biswap, Thena, SushiSwap,
   ApeSwap и Uniswap.
3. **Список наблюдения** — тикеры, пулы которых добираются
   принудительно, даже если по обороту они не проходят никуда.
   Ищутся по имени, адрес указывать не нужно.

   Задаётся файлом `watchlist.txt` в корне проекта: один тикер в строке,
   после `#` комментарий. Файл выбран вместо переменной в YAML намеренно —
   отступ в YAML легко испортить, а ошибка вылезет только при следующем
   прогоне. Переменная `ARB_WATCH_TOKENS` в `collect.yml` тоже работает
   и **складывается** с файлом, а не заменяет его.

   Проверить, что тикер действительно собирается, можно на странице
   «Токены под наблюдением», а что вообще есть по нему в сети —
   командой `python probe_token.py AAVE`: она спрашивает источник
   напрямую и показывает все пулы токена с пометкой, какой порог
   не пустил каждый из них.

   К пулам из списка наблюдения применяется свой порог ликвидности
   (`watch_min_reserve_usd`, 10 000 против общих 100 000) и они не
   вытесняются квотой площадок. Иначе список был бы бесполезен ровно
   там, где нужен: токен, не проходящий в топ по обороту, обычно и по
   размеру пула не проходит общий порог.

При обрезке до `dex_pool_limit` сначала каждой площадке отдаётся её
квота (`dex_venue_quota`), и только остаток разыгрывается по размеру
пула. Квота — минимум, а не потолок: иначе ради разнообразия
выбрасывались бы самые крупные и потому самые исполнимые пары.

**Чего сделать нельзя на бесплатных данных:**

- исторические котировки агрегаторов (KyberSwap, OpenOcean, ParaSwap,
  LI.FI, SushiSwap, Jupiter) — у них нет и не будет исторического API,
  они отвечают только на вопрос «сколько получу сейчас»;
- точная глубина V3-пулов в прошлом — нужна archive-нода или сабграф
  с полной картой тиков;
- межбиржевой спред по акциям и металлам — бесплатные фиды
  консолидированные и с задержкой 15 минут, а консолидированный фид
  по построению не показывает разницу между площадками.

## Монитор

Набор адаптеров с общим интерфейсом. Работают по-настоящему:

- **Спред между крипто-биржами** — один актив на разных площадках;
- **Депег стейблкоинов** — отклонение от номинала, самый надёжный сигнал;
- **Базис спот ↔ перп** — дельта-нейтральная позиция, доход плюс фандинг;
- **DEX против CEX** — цена в пуле BNB Chain против биржевой, котировка
  берётся прямо из смарт-контракта через существующий `dexes.py`.

Акции и металлы — заглушки с рабочей структурой. Если появится платный
фид с котировками в разрезе площадок, достаточно реализовать
`fetch_by_venue()` в `DelayedInstrument` и снять флаг `tradable`.

## Что показано в таблице связок

| Колонка | Смысл |
|---|---|
| Связка | цепочка обменов от стартового актива и обратно |
| Сейчас | маржа в последней точке истории — единственная, что относится к настоящему |
| Макс | лучшая маржа за выбранное окно |
| В плюсе | какую долю времени связка была прибыльна |
| Окно средн | типичная длительность возможности: столько времени обычно есть, чтобы зайти и провернуть обмен |
| Ликвидн. | самый мелкий пул в цепочке — он и ограничивает объём |
| Маршрут | площадки **по порядку исполнения**, пронумерованы: `1·biswap → 2·pancakeswap_v3` |
| Сеть | в какой сети идут обмены |
| Перев. | нужен ли вывод между площадками |
| Токены | расшифровка тикеров маршрута |

Остальные колонки прячутся переключателем «Показать все колонки»: на узком
экране пятнадцать столбцов не помещаются, а решение принимается по восьми.

Под графиком — блок **«Обмены по порядку»**: для каждой ноги площадка, сеть,
ликвидность пула и ссылка «открыть обмен» с уже подставленными адресами
контрактов. Ссылку можно открыть во встроенном браузере кошелька и свопнуть
сразу. Форматы адресов собраны в `links.py`, словарь `SWAP_URL` — если
какая-то площадка сменит адрес страницы, править нужно только там.

### Переводы между площадками

Связка, где все обмены идут в одной сети на DEX, — это последовательность
свопов из одного кошелька. Как только в цепочке появляется биржа или вторая
сеть, между ногами возникает перевод: комиссия сети, время подтверждения,
иногда заморозка вывода. Расчёт этого не учитывает, поэтому такие связки
помечаются в колонке «Перев.» и по умолчанию отфильтрованы переключателем
«Только без переводов».

## Оповещения в Telegram

Считаются после каждого сбора по свежим данным и уходят в чат, если связка
прошла порог. Настраивается двумя секретами в репозитории:

| Секрет | Что это |
|---|---|
| `TELEGRAM_BOT_TOKEN` | токен бота от [@BotFather](https://t.me/BotFather) |
| `TELEGRAM_CHAT_ID` | идентификатор чата — можно узнать у [@userinfobot](https://t.me/userinfobot) |

Без них шаг молча пропускается.

Пороги задаются переменными в `collect.yml`:

```yaml
ALERT_MIN_MARGIN: "0.3"        # чистая маржа сейчас, %
ALERT_MAX_MARGIN: "5"          # выше — считаем артефактом данных, %
ALERT_MIN_LIQUIDITY: "200000"  # минимальный пул в цепочке, $
ALERT_MAX_PER_RUN: "5"         # сколько связок за прогон
ALERT_MUTE_MINUTES: "90"       # сколько молчать о том же наборе токенов
```

Четыре решения, без которых оповещения превращаются в мусор:

- **отбор по марже «сейчас», а не по максимуму за период** — красивый пик
  недельной давности к делу не относится;
- **потолок правдоподобия** — маржа в сотни процентов означает неверную
  цену, а не находку; подробности ниже;
- **порог по ликвидности** — на мелком пуле маржа неисполнима;
- **память об отправленном** — одна связка живёт десятки минут и попала бы
  в каждый прогон; повтор придерживается на `ALERT_MUTE_MINUTES`. Ключ
  памяти — набор токенов, а не подпись маршрута: одна и та же возможность
  приходит в нескольких перестановках и иначе давала бы пять сообщений
  вместо одного.

## Что под наблюдением

Страница «Токены под наблюдением», модуль `inventory.py`. Отвечает на
вопрос, которого не покрывает ни таблица связок, ни график: **проверяется
ли конкретный токен вообще**.

Различие принципиальное. У отсутствия связки две причины, и выглядят они
одинаково:

| Что произошло | Что делать |
|---|---|
| токена нет в данных — о нём никто не спрашивал | добавить в `watchlist.txt` |
| токен есть, связка не сходится по издержкам | ничего, возможности нет |

**Прямой пул — не то же самое, что возможность обмена.** Колонка
«Торгуется с» перечисляет активы, с которыми у токена есть прямой пул.
В кошельке обмен AAVE → DAI пройдёт и без такого пула: роутер сам
разложит его на AAVE → WBNB → DAI. Но в расчёте это две ноги с двумя
комиссиями, а не одна, и связка «USDT–AAVE–DAI–USDT» из трёх шагов
на деле оказывается пятью обменами. Поэтому «прямой пул только с BNB»
не противоречит тому, что вы каждый день меняете этот токен на DAI.

Страница показывает по каждому токену: полное имя, число пар, площадки,
пулы, суммарную ликвидность и оборот, свежесть последней котировки
и участвует ли он в расчёте. Поле «Проверить тикер» даёт прямой ответ
одной фразой — «проверяется», «отсеян», «нет в данных», «мало пар»
(токен торгуется только против одного актива, цикл через него
не замыкается) или «устарел».

Отдельная таблица показывает список наблюдения и по каждому тикеру —
дошли ли до него пулы.

## Разбор связки по шагам

Модуль `breakdown.py`, на странице связок — раздел «Разбор обмена по шагам».
Отвечает на вопрос, которого таблица не покрывает: **что именно я увижу
в кошельке на каждом обмене**.

```
USDT → BNB → CAKE → USDT   объём 1 000.00 USDT
1. 1 000.00 USDT → 1.6638 BNB    курс 0.001664 · pancakeswap_v3 · издержки 0.27% · вклад -0.275%
2. 1.6638 BNB → 484.4401 CAKE    курс 291.1697 · pancakeswap_v3 · издержки 0.30% · вклад +0.897%
3. 484.4401 CAKE → 1 001.85 USDT курс 2.0680   · biswap         · издержки 0.43% · вклад -0.432%
Итог: 1 001.85 USDT − газ 0.45 = +0.140% (+1.40 USDT)
```

Три числа в каждой строке считаются по-разному, и это важно понимать.

**Суммы** берутся из тех же курсов, по которым строилась таблица, —
не пересчитываются заново по другой формуле. Поэтому итог разбора
совпадает с маржой в таблице до шестого знака; это проверяется тестом.
Их и надо сверять с тем, что показывает кошелёк перед подтверждением.

**Издержки** раскладываются обратно: исполнимый курс равен споту,
умноженному на (1 − комиссия) и на проскальзывание. Комиссия площадки
известна точно, проскальзывание для пула считается по резерву. Отсюда
восстанавливается спот — курс без издержек.

**Вклад ноги** — изменение стоимости позиции, пересчитанной в стартовый
актив по срединному курсу. Срединный курс берётся как корень из
отношения прямого и обратного исполнимых курсов: издержки в них
направлены в разные стороны и при делении сокращаются. Вклады
перемножаются ровно в итоговую маржу — это тождество, а не оценка.

Практический вывод виден сразу: маржа почти никогда не размазана по
цепочке. Одна нога даёт плюс, остальные отнимают на комиссиях, и весь
вопрос в том, перевешивает ли первое второе.

Сумму можно менять: проскальзывание пересчитывается под неё, и видно,
как связка ведёт себя на 100 долларах против 10 000. Газ при этом
не зависит от суммы — поэтому на маленьком объёме он и съедает всё.

## Отсев недостоверных данных

Модуль `quality.py`. Появился после конкретного случая: в чат ушли пять
оповещений о связке «USDT → BNB → MARSCOIN → USDT, +578%». Столько
не бывает — реальный арбитраж на ликвидных парах живёт в долях процента.

Три механизма, из-за которых цена оказывается неверной, и что с ними
делается:

| Механизм | Почему возникает | Что делает отсев |
|---|---|---|
| Один тикер — разные токены | сетка адресуется по символу, а завести в сети BNB токен с чужим символом стоит копейки | символ разводится по адресам контракта: настоящим считается канонический, иначе тот, за которым больше оборота; пулы остальных выбрасываются |
| Накрученный резерв | долларовая оценка пула считается по цене токена, а цену задаёт тот же пул | фильтр по обороту за сутки: встречные сделки подделать дороже |
| Неисполнимая цена | налог на перевод, заблокированная продажа, пул без сделок | потолок правдоподобия на итоговую маржу |

Отсев ничего не удаляет из базы — он только не пускает данные в расчёт.
В интерфейсе есть переключатель «Отсеивать недостоверные пулы» и поле
«Потолок правдоподобия, %»: порог всегда можно поднять и посмотреть,
что именно скрылось. Что отсеяно и почему, показывает раскрывающийся
список над таблицей.

В сообщении: маршрут, маржа, сеть, узкое место по ликвидности, типичное окно,
ссылка на обмен для каждой ноги и оговорка, что расчёт исторический и окно
могло закрыться.

## Проверки

```bash
python -m history.tests.test_math       # математика, данные с известным ответом
python -m history.tests.test_pipeline   # сквозной прогон, без сети
python -m history.tests.test_snapshot   # снимок туда-обратно и память
python -m history.tests.test_cex_resilience  # поведение при отказах бирж
python -m history.tests.test_alerts     # отбор и текст оповещений
python -m history.tests.test_quality    # отсев недостоверных данных
python -m history.tests.test_inventory  # инвентарь токенов
python selftest.py                      # доступность внешних источников
```

`test_math` подкладывает рынок с заранее заложенной связкой и требует,
чтобы поиск нашёл именно её, а маржа совпала с теоретической до шестого
знака. Отдельно проверяется, что на согласованных курсах связок
не находится вообще — то есть ложных срабатываний нет.

`test_pipeline` пишет синтетические свечи в настоящую базу и прогоняет
весь путь до данных графика, проверяя в том числе, что прибыльное окно
обнаружено ровно там, где было заложено.

`test_quality` воспроизводит ту самую подделку: два пула с тикером CAKE,
за которыми стоят разные контракты, и цена одного в тридцать раз выше.
Без отсева поиск находит связку с маржой в тысячи процентов, с отсевом —
не находит вовсе.

## Что этот инструмент не делает

История не позволяет торговать. Её ценность в другом: увидеть, как часто
возникает спред по конкретной связке, сколько он живёт, какая доля
находок — артефакт данных, а какие пары структурно стоят внимания.

На BNB Chain всё, что видно на минутной истории, забирают MEV-боты
в том же блоке. Практический смысл — аналитика и отбор пар, а не
торговый сигнал для ручного исполнения. Короткие одиночные всплески
на графике почти всегда неисполнимы; интерес представляют связки
с высокой долей прибыльного времени и длинными окнами.

Перед любой реальной сделкой прогоняйте найденное через основной
калькулятор — он считает по настоящему стакану с реальной глубиной.
